# Writer Design

## Purpose

The writer will eventually add or update Native Instruments-compatible metadata in WAV files. This is the first project area that can modify files, so it needs stricter guarantees than the read-only parser, indexer, metadata observer, and byte coverage validator.

The initial writer should be conservative:

- preserve audio bytes exactly
- update only explicitly targeted metadata bytes
- validate the generated file before exposing it as a final result
- prefer writing a new output file over modifying an original file in place
- treat every known byte-coverage tolerance as an explicit normalization step

## Core Principle

The writer should use a `Read -> Plan -> Build -> Validate -> Commit` workflow.

This is close to established patterns from transactional systems and safe file replacement:

- databases use transactions with validation before commit
- compilers separate parsing, transformation, and output generation
- safe file writers commonly write to a temporary file, flush it, validate it, then atomically rename it

For this project, the workflow is intentionally file-oriented rather than database-like. A WAV rewrite cannot be rolled back by the filesystem after arbitrary partial writes, so the writer should avoid mutating the source file until the new bytes are fully built and validated.

## Workflow

### 1. Read

Read the source file as immutable input.

Required checks:

- build the byte coverage map
- run write-safety validation
- reject files outside the selected writer strategy
- identify exact source regions that the strategy may replace
- compute the original audio `data` chunk hash

For writer v1, the target strategy should be:

```text
safe_to_update_existing_metadata
preserve_audio_update_existing_id3_geob
```

The first version should not handle files that require new ID3 chunks, new GEOB frames, multiple SoundInfo payload review, or ambiguous metadata placement.

### 2. Plan

Create a write plan without producing output bytes yet.

The write plan should describe:

- source path
- output path
- selected strategy
- original byte regions used as anchors
- metadata regions to replace
- byte ranges that must remain unchanged
- required size updates, for example RIFF size, ID3 tag size, GEOB frame size, and ID3 chunk size
- normalizations to apply

The plan should be serializable to JSON for debugging. This gives us an audit trail before we trust the writer.

### 3. Build

Build the complete output bytes in memory or into a temporary file.

Important constraints:

- never modify the source file during build
- preserve the `data` chunk payload byte-for-byte
- preserve unrelated chunks unless a strategy explicitly allows normalization
- recalculate all affected container sizes from the generated bytes
- keep RIFF chunk padding correct after odd-sized payloads

The first implementation can build a full output file from byte slices:

1. copy bytes before the target metadata region
2. insert newly generated metadata bytes
3. copy bytes after the target metadata region
4. update affected length fields

This is simpler and safer than editing bytes in place, because metadata size may change.

### 4. Validate

Validate the generated output before commit.

Required validation:

- byte coverage map has no errors
- write-safety validation returns an expected safe status
- original audio `data` chunk hash equals output audio `data` chunk hash
- intended metadata can be parsed back
- generated metadata summary matches the requested tags
- RIFF declared size equals the physical output file size unless a strategy explicitly emits a known tolerance, which writer v1 should not do

Validation should operate on the generated output file/bytes, not on the source file.

### 5. Commit

Commit should expose the validated output to the user.

Preferred first behavior:

```text
source.wav -> output.wav
```

The writer should create a new file by default. This protects the original dataset and makes manual inspection easy.

Later, optional in-place writing can be added through a separate explicit flag. In-place mode should still be implemented through safe replacement:

1. write output to a temporary file in the same filesystem/directory
2. flush and close the temporary file
3. validate the temporary file
4. optionally create/keep a backup
5. atomically replace the original file

## Output Modes

### Copy Mode

Default mode. The source file is never modified.

Example future CLI shape:

```bash
sth write-tags source.wav --output tagged.wav
```

This should be the first implemented mode.

### Directory Mode

Write many outputs into a target directory while preserving relative paths.

Example future CLI shape:

```bash
sth write-tags --dataset --output-root /path/to/tagged-samples
```

This is useful for testing against a whole dataset without touching originals.

### In-Place Mode

Explicit and later only.

Example future CLI shape:

```bash
sth write-tags source.wav --in-place --backup
```

This mode should remain unavailable until copy mode is well-tested.

## Writer Strategies

### v1: Update Existing ID3 GEOB

Target policy output:

```text
write_safety = safe_to_update_existing_metadata
write_strategy = preserve_audio_update_existing_id3_geob
```

Allowed:

- replace the existing NI SoundInfo/GEOB metadata payload
- update affected ID3 and RIFF size fields
- preserve all audio bytes

Not allowed:

- create a new ID3 chunk
- create a new GEOB frame in an otherwise empty ID3 tag
- choose among multiple NI SoundInfo payloads
- emit known byte-coverage tolerances

### v2: Normalize Then Update Existing ID3 GEOB

Target policy output:

```text
write_safety = safe_with_normalization_to_update_existing_metadata
write_strategy = normalize_then_update_existing_id3_geob
```

Allowed:

- same as v1
- normalize known container tolerances during rewrite

Examples:

- fix RIFF size that is one byte beyond physical file size
- insert missing chunk padding when rewriting surrounding bytes
- remove or regularize tolerated trailing zero padding

This should come after v1 because normalization increases the amount of generated structure we need to verify.

### v3: Insert GEOB Into Existing ID3

Target policy output:

```text
write_safety = read_only
write_strategy = unsupported_missing_ni_soundinfo_payload
```

These files have an ID3 chunk but no mapped NI SoundInfo payload. Some may contain an empty ID3 tag.

This strategy should remain separate because it needs to construct new ID3 frames rather than replace a known existing one.

### v4: Append New ID3 Chunk

Target policy output:

```text
write_safety = read_only
write_strategy = unsupported_missing_id3_chunk
```

These files have no ID3 chunk. The strategy likely needs to append a new `ID3 ` RIFF chunk and update the RIFF size.

This should come last because it changes the top-level chunk layout.

## Mandatory Safety Invariants

The writer must enforce these invariants before commit:

- output file exists only after successful validation
- source file remains unchanged in default mode
- output audio hash equals source audio hash
- output byte coverage is `safe_to_rewrite`
- output write safety is compatible with the selected strategy
- no unknown diagnostics are introduced
- all changed byte ranges are explained by the write plan
- all length fields match generated byte sizes

## Open Design Questions

- Should generated metadata include both SoundInfo UTF-16LE structures and MessagePack tag objects from the start?
- Which NI fields are mandatory for Maschine/Kontakt compatibility?
- How should category paths be selected when multiple source observations disagree?
- Should writer plans be stored in PostgreSQL before writing outputs?
- Should output files receive deterministic names, or should callers fully control output paths?
- Should v1 replace the whole GEOB frame or only the SoundInfo payload inside it?

## Recommended Next Step

Before implementing the writer, build a read-only write plan generator for one `safe_to_update_existing_metadata` file.

The plan generator should output JSON and include:

- source file
- proposed output file
- selected strategy
- source audio hash
- target RIFF chunk
- target ID3 chunk
- target GEOB frame
- target SoundInfo payload
- byte ranges to preserve
- byte ranges to replace
- size fields that would need recalculation

Once the plan looks correct for real files, the actual byte-building step can be added behind a dry-run-first CLI.
